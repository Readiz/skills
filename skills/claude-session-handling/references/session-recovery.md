# 재시작과 기존 대화 복원

## 변경 전 기준

`inspect_sessions.py`는 등록된 프로세스만 읽는다. 이미 내려간 대화는 목록에 없을 수 있다. 사용자가 복원하려는 대화 목록과 비교해 예상 ID를 별도로 확보한다. 과거 특정 실행의 PID, 서비스 이름, 환경 ID와 대화 ID를 새 작업의 상수로 쓰지 않는다.

1. 기존 LaunchAgent의 label, 등록 domain, 실제 명령, WorkingDirectory와 로그 경로를 확인한다. 필요한 표준 경로는 `~/Library/LaunchAgents/`다. 사용자 계정과 작업 폴더 신뢰가 맞는지 먼저 확인하며 `/`나 다른 폴더를 대신 신뢰하지 않는다.
2. 로컬 대화 ID와 원격 대화 ID를 짝짓고 PID, 상태와 모델의 확인 근거를 기록한다. 실제 세션 종류가 다를 수 있으므로 background, interactive, Remote Control의 SDK 실행을 구분한다.
3. `busy`라면 실제 자식 작업을 확인한다. Blender 렌더링, 다운로드나 빌드를 조용히 종료하지 않는다. 사용자가 중단까지 승인했다면 이를 따르고, 아니면 해당 영향과 대기 선택을 확인한다. 정상 종료 신호도 자식 작업에 영향을 줄 수 있다.
4. 관련 대화 파일과 설정, 복원 메타데이터를 비공개로 백업한다. 데이터 크기와 여유 공간을 확인하고 제한을 둔다. APFS라면 `cp -c`의 지원 여부를 확인해 공유 복사를 쓸 수 있다. 대규모 이력은 기존 NAS 운영 규칙을 따른다. 해시나 manifest만 만든 것을 실제 백업이라고 부르지 않는다.

## 공식 재개 경로부터 확인한다

현재 설치본의 `claude remote-control --help`, `claude respawn --help`, `claude --help`와 공식 문서를 확인해 세션 종류에 맞는 경로를 선택한다. 명령의 존재와 실제 복원 성공을 구분한다.

- 다중 세션 서버를 재시작하면 시작 대화만 먼저 실행되고 다른 대화는 나중에 다시 생길 수 있다. 문서의 전체 복원 설명만으로 모든 로컬 PID가 즉시 재생성된다고 약속하지 않는다.
- `remote-control --continue`나 `--session-id`의 대상 수, spawn/capacity 옵션과의 충돌 조건을 현재 버전에서 확인한다. 같은 환경이 이미 제공 중이라는 오류가 나면 별도 서버를 계속 늘리지 않는다.
- background 세션용 `respawn`을 모든 Remote Control 자식 프로세스의 재시작 명령으로 취급하지 않는다.
- `--bg --resume ... --remote-control` 조합은 원격 연결을 새로 만들 수 있다. 같은 로컬 대화가 열렸더라도 원래 원격 ID인지 확인한다. 시험 과정에서 새 실행을 만들었다면 이번 작업이 만든 실행만 중지한다. 원래 대화를 `purge`나 `rm`으로 정리하지 않는다.
- `launchctl submit`으로 만든 프로세스는 호출한 셸의 작업 폴더를 그대로 쓰지 않을 수 있다. 명시적인 WorkingDirectory가 있는 정상 운영 방식을 사용하고 `/` 신뢰 오류를 인증 장애로 오해하지 않는다.

사용자가 승인한 서버 하나에만 필요한 종료/재시작을 수행한다. 단순 재시작은 기존 실행 설정과 capacity를 유지한다. 새 LaunchAgent, background 서비스나 계속 재시도하는 임시 프로세스를 만들었다면 원래 운영과 구분하고 자신이 만든 불필요한 실행만 정리한다.

## 내부 복원 정보는 표준 수리 도구가 아니다

`bridge-pointer.json` 같은 비공개 메타데이터나 내부 재연결 API를 기본 경로로 사용하지 않는다. 버전별 스키마, 대상 ID와 소유 환경, 실제 부작용을 확인하지 않은 채 기록을 덮어쓰지 않는다. 내부 코드에서 필드나 endpoint를 찾았다는 사실만으로 지원되는 운영 절차가 되지는 않는다.

저장용 `session_...`와 실행/API용 `cse_...`처럼 같은 대화를 가리키는 ID 표현이 다를 수 있다. 로컬 UUID와도 다르다. 실패한 요청의 원인을 확인하기 전에 임의 변환으로 재전송하지 않는다. 실운영에서 검증되지 않은 복원 POST나 내부 필드 수정 스크립트를 스킬에 재사용 도구로 넣지 않는다.

승인 거절이 난 동작은 다른 도구, 직접 API 호출, 별도 프로세스나 나중에 실행하는 예약 작업으로 옮겨 실행하지 않는다. 독립적으로 허용되는 안전한 대안이 기존 접근 범위를 우회하지 않는지 확인한다. 정상적인 대안이 없으면 차단된 범위와 필요한 결정을 명확히 남긴다.

## 검증 경계

| 확인한 증거 | 말할 수 있는 결과 |
| --- | --- |
| launchd의 새 서버 PID, 연결 로그 | 서버가 재시작되고 연결됨 |
| 재연결 요청의 HTTP 200 | 요청 접수, 대화 실행 재개는 별도 |
| 같은 원격 ID와 로컬 ID의 새 PID | 해당 대화의 실행 재개 |
| 시작 인수의 모델 | 시작 때 지정한 모델 |
| 현재 모델 표시나 최신 실제 응답 | 해당 시점의 모델 확인 |
| 정의 파일 존재/구문 검사 | 서브에이전트 정의 설치 |
| 로딩 목록과 실제 Agent 호출, 하위 응답 모델 | 서브에이전트 인식과 위임 실행 |

예상 대화 ID 전체와 결과를 대조한다. 로컬 등록 목록이 시간에 따라 변할 수 있으므로 일부 대화가 내려간 이유를 확인하고 전체/일부 완료를 구분한다. 원격 API가 상태 대신 다른 응답 구조를 주면 200만 보고 상태를 추측하지 않는다.

재개 뒤 관측할 시간이나 조회 횟수의 상한을 먼저 정한다. 예상 시작 시간 안에 새 증거가 없으면 미재개 대화와 마지막 확인 시각을 보고하고 같은 결과의 재시작/재연결 요청을 반복하지 않는다. 추가 시도는 오류 원인이나 대상 상태가 바뀌었거나 현재 버전의 다른 지원 경로를 확인했을 때 판단한다. 관측 상한이 지났다는 이유만으로 busy 작업을 종료하거나 복원이 불가능하다고 단정하지 않는다.

네이티브 재개나 compaction은 JSONL을 재작성할 수 있다. 바이트나 파일 크기 변경만으로 대화가 사라졌다고 단정하지 않되, 이전 바이트가 보존됐다고도 하지 않는다. 변경 전 백업을 유지하고 원래 대화의 ID와 의미 있는 마지막 기록, 재개 결과를 확인한다. 최종 보고에는 확인한 범위와 부족한 증거를 나눈다.

운영 로그, 실제 ID, 대화 원문과 백업 경로는 사용자 비공개 기록에 남긴다. 공개 스킬에는 이 절차와 일반화된 실패 조건만 반영한다.
