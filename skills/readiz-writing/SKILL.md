# Readiz 글쓰기

독자가 글만으로 내용을 이해하고 판단하거나 활용할 수 있게 쓴다. Readiz의 직접적이고 편한 문체를 기본으로 하되, 사용자가 지정한 독자·분량·어조·장르를 먼저 따른다.

이 스킬은 글의 작성과 퇴고를 담당한다. 독립적으로 사용할 수 있으며 특정 사이트나 다른 스킬이 필요하지 않다. 저장·첨부·게시·자료 위키 축적은 요청받은 작업이나 이를 호출한 스킬의 절차로 처리하며, 이 스킬만 사용했다는 이유로 시작하지 않는다.

## 글의 목적에 맞추기

- 블로그 해설·분석은 중심 질문과 판단을 세우고 근거로 전개한다. 이런 글을 쓸 때는 [논지 구성·검증·퇴고](references/analysis.md)를 읽는다. 투자 글의 평가 범위와 시세 차트 기준도 그 문서에 있다.
- 방법·기술 기록은 준비, 행동, 작동 원리, 확인할 결과를 연결한다. 자료 문서·위키는 정의, 출처, 해석 범위와 재사용할 내용을 중심으로 쓴다. 이런 글에 주장형 결론이나 전체 외부 조사를 억지로 요구하지 않는다.
- 요약·번역·문장 교정은 요청한 범위와 길이를 보존한다. 짧은 요약을 장문 분석으로 확대하거나, 일반 채팅 답변에 이 스킬의 글 구조를 강제하지 않는다. 기존 글을 고칠 때는 사용자의 내용과 의도를 먼저 보존한다.

## 설명의 깊이

- 초안도 독자가 그대로 읽을 수 있는 글로 작성한다. 사용자 질문에 대한 부가 답변, 제목·URL의 의미 확인, 후속 글 검색 결과, 도구 사용·저장 과정 등 작업 보고는 채팅에서 전달하고 본문·제목·설명에 넣지 않는다. 사용자가 그 확인 과정 자체를 글의 주제로 요청한 경우는 예외다. 글의 이해에 필요한 데이터 기준 시점, 발언의 귀속, 가정·한계와 출처는 본문에 간결하게 남긴다.
- 사용자의 **초안 요청은 상세한 설명을 갖춘 완결된 글을 요청하는 것**이다. 짧은 요약을 명시적으로 요청하지 않았다면 핵심만 대충 압축해 끝내지 않는다. 특히 유튜브 초안은 **영상을 보지 않아도 핵심 개념·사례·원인과 결과를 이해하고, 다룬 내용을 판단하거나 활용할 수 있는 수준**으로 작성한다. 방법·실습 영상은 필요한 준비, 단계별 행동, 확인할 결과까지 글만으로 따라갈 수 있게 설명하고, 해설·분석 영상은 근거와 작동 방식, 조건에 따라 판단이 달라지는 이유까지 풀어 쓴다. 필요한 본문 분량과 실제 유튜브 장면은 충분히 늘린다.
- 사용자가 실제로 겪거나 측정했다고 확인하지 않은 경험·성능 수치를 1인칭 사실로 만들지 않는다. 기술 설명의 가정, 한계, 확인하지 않은 부분을 구분하고, 조사한 주장은 본문 근처의 출처 링크로 연결한다.

## 문체

핵심 내용을 선명하게 쓰고, 의견을 밝히는 글에서는 판단을 바로 말한 뒤 필요한 이유를 충분히 붙인다. 친절한 교과서식 해설보다 사용자가 직접 정리한 글의 호흡을 따른다.

- 문체를 맞출 때는 사용자가 제공·지정한 원작성 글 두세 편을 먼저 읽는다. Readiz의 공개 예시는 [Svelte vs React](https://www.readiz.com/blog/study/til/svelte_vs_react/)와 [오답노트](https://www.readiz.com/blog/viewings/miscellaneous/mistake/)다. 최근 AI 초안을 사용자의 문체 기준으로 삼지 않는다. 예시의 표현 방식만 참고하며, 과거의 사실 판단이나 글쓴이의 경험을 새 글로 옮기지 않는다. 예시에 접근하지 못하면 읽었다고 하지 않고 아래 기준과 제공된 글로 진행한다.
- 원작성자가 평소 잘 쓰지 않는 문장부호나 장식 기호는 쓰지 않는다. 특히 제목, 본문, 캡션에서 중앙점(`·`)으로 단어를 묶어 나열하지 않는다. `원인·과정·결과`는 `원인과 과정, 결과`처럼 쉼표나 자연스러운 접속 표현으로 풀어 쓴다. 인용 원문, 고유명칭, 코드, 수식에서 기호 자체가 의미를 갖는 경우에는 보존한다. 퇴고할 때 문장부호도 원작성자의 사용 습관과 맞는지 확인한다.
- 익숙한 말로 쓰되 모든 문장을 “~다”로 끝내지는 않는다. 본문은 문맥과 호흡에 맞게 평서문·질문·명사형을 섞고, 캡션이나 짧은 설명은 “공시 기준으로 그림”, “예상 이익 비교”처럼 간결하게 끝낸다. 어미를 바꾸려고 자연스러운 문장을 억지로 끊지는 않는다. “이 관점을 적용하면”, “함께 살펴볼 필요가 있다”, “내 결론은 분명하다” 같은 전개 예고를 빼고 바로 내용을 쓴다. 의견마다 “나는 …로 본다”를 반복하지 않는다.
- 핵심 주장·근거·판단과 이를 이해하고 활용하는 데 필요한 설명을 남긴다. 중복과 무관한 설명은 덜어내되 독자가 이미 알 것이라고 가정해 필요한 개념·중간 과정·예시를 생략하지 않는다. 도표의 숫자를 본문에서 전부 다시 나열하지 않는다. 짧은 글에 목차나 소제목을 억지로 만들지 않는다.
- 영상의 발언을 그대로 전사하지 않고 독자가 따라갈 수 있는 순서로 재구성한다. 핵심 내용의 범위와 설명의 깊이는 보존하고, 같은 내용을 되풀이하는 부분만 줄인다. 자료를 보강할 때는 그 근거가 주장에 어떻게 연결되는지 필요한 만큼 설명한다.
- 실제로 하지 않은 투자·체험은 만들지 않는다. 원래 글의 직접적이고 편한 표현은 살리되, 농담·말줄임표·감탄사를 억지로 붙여 사람다운 척하지 않는다.

## 자료와 시각 자료

- 웹 글을 바탕으로 작성할 때는 본문 이미지·도표도 확인한다. 텍스트 추출 결과에 이미지가 없다는 이유로 원문에도 없다고 판단하지 않는다. 원문 페이지나 HTML의 이미지·원본 링크를 살펴보고, 본문 설명에 도움이 되는 자료를 선별해 해당 문단 가까이에 첨부한다. 장식용 사진·광고·중복 이미지까지 일괄 복제하지 않는다.
- 실제 이미지를 열어 내용·축·단위·기준 시점·가독성을 확인한다. 작은 썸네일보다 원문이 연결한 선명한 원본을 사용하고, 이미지 속 수치와 본문 설명이 맞는지 대조한다. 출처 표기나 범례를 지우지 않는다.
- 대체 텍스트와 짧은 한국어 캡션을 붙인다. 캡션에는 이미지가 보여주는 내용과 원문 출처를 연결하고, 원문이 다른 제작자나 데이터 제공자를 밝히면 그 표기도 보존한다. 원문 이미지와 직접 만든 설명용 도표를 구분한다.
- 숫자를 전달하는 차트는 실제 데이터로 그리며 생성 이미지로 꾸미지 않는다. 자료가 없거나 실제 이미지를 확보하지 못했으면 꾸며 넣지 않는다. 제한은 채팅에 알리고 확보한 근거로 글을 완성한다.

## 전달·저장 전 필수 문체 검토

직접 작성하거나 수정한 글은 **최종 제목, 소개, 본문, 표 앞뒤 설명과 캡션을 검토한 뒤에만 전달하거나 저장한다.** 일반 글, 기술 설명, 자료 문서와 LLM Wiki에 모두 적용하며 새 초안과 기존 글 수정에도 동일하다. 아래 검토를 마치기 전에 `create`, `update`, 저장 API나 게시 도구를 호출하지 않는다. 이 검토는 작성자가 수행하며 사용자의 추가 승인이나 본문 속 점검표로 바꾸지 않는다.

1. 최종 원고 전체를 읽고 설명 뒤에 덧붙인 부정, 면책, 오독 경고를 찾는다. 앞에서 밝힌 범위를 다시 방어하거나, 글이 주장하지 않은 해석을 만들어 부정하는 문장은 고친다. 해설·분석은 [회피성 전개를 막는 퇴고](references/analysis.md#회피성-전개를-막는-퇴고)도 수행한다.
2. 각 문장을 빼면 독자가 이해할 사실, 적용 조건, 행동이 실제로 달라지는지 판단한다. 달라지는 것이 없으면 삭제하고 앞뒤 설명을 바로 잇는다. 설명용 예제라고 밝혀 놓고 “실제 분석기의 결과를 재현한 표는 아니다”를 붙이거나, 설계 방법을 소개하면서 “특정 엔진의 필수 규칙은 아니다”를 덧붙이는 전개가 해당한다.
3. 필요한 조건은 설명 안에 한 번만 넣는다. 예를 들어 “다음은 원리를 보여주기 위해 만든 예제다. 실제 분석기의 결과를 재현한 표는 아니다”는 “다음 세 문서를 공백으로 나누어 역색인을 만든다”로 고친다. 단순화한 예시, 가정한 수치, 측정 범위, 버전과 실제 기능 제약은 정확히 남긴다. 원문 인용이나 오류를 바로잡는 데 필요한 부정까지 일괄 삭제하지 않는다.
4. 수정한 문단을 앞뒤 문단과 이어 읽어 불필요한 경고와 중복이 사라졌는지 확인한다. “아니다”를 “구분해야 한다”나 “주의가 필요하다”로 바꿔 같은 방어 내용을 남기지 않는다. 부정어 검색은 후보를 찾는 보조 수단이며 검색 결과 0건을 검토 완료로 삼지 않는다.
5. 검토한 최종 원고와 실제 저장할 내용을 대조한 뒤 저장한다. 검토 후 문장을 추가하거나 바꿨으면 해당 부분과 앞뒤 문맥을 다시 검토한다. 저장 후 반환된 본문과 버전에서도 수정 사항이 유지됐는지 확인한다.

독자가 원문이나 영상을 다시 열어야만 이해할 수 있는 핵심 빈칸이 없는지도 확인한다. 글의 목적에 필요한 설명, 근거와 예시는 남기고 반복과 작업 보고를 덜어낸다. 자료 문서와 위키는 정의, 출처와 미확인 범위를 정확히 정리하고, 방법 글은 필요한 행동과 결과가 이어지는지 확인한다.

글의 완성도와 저장·렌더링 성공은 별도로 판단한다. 문체를 맞췄다는 이유로 사실 검증이나 기술 검사가 끝났다고 보고하지 않는다.
