# 웹 크롤링 구현과 진단

사용자가 지정한 출처와 수집 범위를 유지하면서 실제 새 자료가 들어오는 수집기를 만든다. 동작 중인 브라우저, 정기 수집기, 저장 데이터, 후속 분석의 성공을 각각 확인한다.

## 시작할 때

- 해당 프로젝트의 실행 명령·스케줄·출처 설정·상태 파일·배포 절차를 먼저 읽는다. 현재 운영 프로세스가 어느 checkout과 런타임을 사용하는지 확인한다.
- 최근 실제 요청 로그와 저장된 글 ID·본문·관측 시각을 대조한다. 파일 수정 시각이나 스케줄 실행 횟수만으로 수집 성공을 판단하지 않는다.
- 403/429 등 HTTP 오류, 응답 없음, 응답 후 파싱 오류, 요청 전 대기, AI 처리 실패를 분리한다. 기존 상태가 원인을 구분하지 못하면 그 사실을 남긴다.
- 공식 API·피드가 있으면 현재 사용 조건과 필요한 내용의 제공 범위를 확인한다. 뉴스 RSS나 시세 API가 게시판 댓글을 대체한다고 가정하지 않는다. 기존 인증정보를 임의로 다른 서비스에 전달하지 않는다.

## 실패하면 오류 본문부터 확인

헤더 수정·원인 추측·재접속보다 **실제 오류 문구 확인과 사용자 보고가 먼저**다. 실패를 진단할 때는 [오류별 대응표](references/error-handling.md)의 해당 항목을 읽는다.

- 이미 받은 응답·저장 HTML·열린 페이지에서 제목과 오류 본문, 최종 URL, 실제 HTTP 상태, 오류 코드를 읽는다. 필요하면 같은 페이지의 스크린샷으로 확인한다. 오류 화면을 보려고 새로고침부터 하지 않는다.
- `Sorry, you have been blocked`, `Access denied` 같은 문구가 실제 오류 화면에 있으면 **접근 차단이 표시됐다는 사실을 즉시 사용자에게 알린다.** 원인이나 차단 해제 방법을 알아낼 때까지 보고를 미루지 않는다. 본문에 인용된 단어만으로 차단을 판정하지 않는다.
- 확인된 현상과 원인 가설을 분리한다. 차단 화면은 차단의 증거지만 그 자체가 IP 차단·요청 과다·특정 헤더 원인의 증거는 아니다. 반대로 원인을 모른다는 이유로 명백한 차단을 단순한 파싱 실패로 축소하지 않는다.
- 명시적 접근 차단이면 해당 공급자의 추가 진단 요청을 멈춘다. 운영 변경이 승인된 범위에서는 해당 공급자의 자동 재시도도 중단하고 상태를 확인한다. 읽기 전용 조사라면 자동 수집의 활성 여부와 중단 필요를 보고한다. 다른 출처까지 일괄 중단하지 않는다.
- 로그가 상태 코드만 남겼다면 `본문 미확보`로 보고한다. 수집기를 수정하는 범위라면 오류를 던지거나 브라우저를 닫기 전에 같은 응답의 제한된 본문과 제목을 읽어 안전한 진단 정보를 남기도록 고친다. 승인되지 않은 재접속으로 누락된 증거를 채우지 않는다.

## 브라우저와 헤더

`실제 Chrome 사용`과 `일반 브라우징과 같은 요청`은 다른 주장이다. HTTP 클라이언트인지 브라우저인지, headless 여부, 새 문맥인지 지속 세션인지부터 확인한다.

오류 본문을 분류한 뒤, 요청 설정 차이가 원인 후보로 남으면 아래 항목을 조사한다. 명시적 차단이 이미 확인됐다면 로컬 비교부터 수행하고 이를 추가 사이트 접속의 근거로 삼지 않는다.

- 문서 요청의 `User-Agent`, `Accept`, `Accept-Language`, `Sec-CH-UA`와 플랫폼 정보
- 페이지의 `navigator.userAgent`, Client Hints, 언어와 자동화 상태
- 쿠키 유무·세션 수명·리다이렉트, JavaScript 실행·콘텐츠 대기 조건, 차단한 하위 리소스
- 응답 코드·콘텐츠 타입·챌린지 표시. 403만으로 IP 차단이나 특정 헤더 원인을 확정하지 않는다.

프로젝트에 Playwright가 있으면 [로컬 브라우저 진단 스크립트](scripts/inspect-browser.mjs)를 사용할 수 있다.

```sh
node /path/to/readiz-web-crawling/scripts/inspect-browser.mjs --project /path/to/project
# GUI가 있는 환경에서 창 모드도 비교하려면 --headed 추가
```

스크립트는 임시 문맥의 탐색을 로컬 응답으로 가로채며 수집 대상 사이트에 요청하지 않는다. 기본 headless와 같은 버전의 표준 Chrome UA를 비교한다. 브라우저나 의존성은 자동 설치하지 않으며 사용자 브라우저 프로필을 열지 않는다.

`HeadlessChrome` 표시가 확인되면 원인 후보로 취급한다. 변경이 적절한 작업에서는 설치된 브라우저가 제공하는 UA에서 제품 표시만 조정하고, 헤더·JavaScript·Client Hints의 버전 일치를 검증한다. 오래된 UA 문자열을 복사하거나 모든 403에 같은 변경을 적용하지 않는다. 이 로컬 비교가 사이트 접근 성공을 증명하지는 않는다.

한 번에 한 조건을 바꾼다. UA 변경과 지속 세션·리소스 제한 해제·프록시 변경을 섞으면 원인을 분리할 수 없다. 자동화 상태 은폐나 CAPTCHA 해결을 기본 해결책으로 넣지 않는다. 세션 유지가 필요한 경우에는 수집기 전용 프로필과 수명·디스크 상한을 정하고 개인 브라우저의 쿠키·로그인 세션과 분리한다.

## 요청량과 복구

- 기존 공급자별 잠금·요청 간격·예산·timeout·Retry-After·cooldown을 유지한다. 진단용 스크립트도 같은 상태를 존중한다. 수정 검증을 이유로 상태 파일을 초기화하거나 IP·계정·경로를 바꿔 즉시 재시도하지 않는다.
- 재시도가 허용되는 일시 오류는 기존 정책의 다음 실행에서 변경을 검증한다. 명시적 차단이나 반복 챌린지는 해당 공급자 요청을 중단하고 마지막 정상 자료를 보존한다. 로컬 cooldown 만료는 사이트 차단 해제의 증거가 아니며, 중단한 공급자를 시간 경과만으로 재개하지 않는다. 사용자에게 원문 오류·영향 범위·중단 상태를 보고하고 기존에 승인된 재개 조건이 있는지 확인한다. 추가 우회나 유료 API 구매를 사용자 요청의 기본 범위로 확대하지 않는다.
- 읽기만 요청받았다면 원문·스케줄·상태를 변경하지 않는다. 수정과 배포는 사용자의 기존 승인 범위와 저장소 지침에 맞춰 수행한다.
- 자신이 만든 브라우저·문맥·서버만 정리한다. 다른 작업이나 개인 세션을 닫지 않는다.

## 저장과 후속 처리

- `publishedAt`(작성), `observedAt`(수집), 댓글 관측, 아카이브 반영 시각을 구분한다. 재시도 중 파일을 다시 저장해도 마지막 정상 관측 시각은 바꾸지 않는다.
- ID와 본문 해시로 신규·기존·변경을 구분한다. 파싱 후보 수, 허용 수, 본문 선택 수, 실제 댓글 수, 제외 사유를 별도로 기록한다.
- 댓글 미수집·일부 수집·이전 관측 재사용을 구분한다. 댓글이 안 보인다는 이유로 댓글 0개나 동의 여론을 추론하지 않는다.
- 완성본을 임시 파일에서 원자적으로 교체한다. 실패 시 기존 정상 데이터를 유지하고 출처별 오래됨·실패 상태를 표시한다.
- 원문 수집과 AI 요약·알림 게시를 별도로 검증한다. 모델 이름이나 호출 성공만으로 요약 품질을 보장하지 않는다. 실제 입력 ID와 출력·게시 ID를 연결한다.

## 검증과 완료 보고

변경에 맞는 검증을 고른다. 파서 변경이면 실제 구조의 표본과 날짜·중복·누락을, 요청 설정 변경이면 실제 브라우저 헤더와 기존 대기 정책을 검증한다. HTTP 200뿐 아니라 예상 본문이 파싱·저장되고 후속 소비자가 그 자료를 읽는지 확인한다.

로그에는 상태 코드·안전한 브라우저 정보·개수·해시와 민감정보를 제거한 오류 제목·짧은 문구·오류 코드 등 필요한 진단 정보만 허용 목록으로 남긴다. 오류 페이지의 IP·이메일·요청 식별값과 스크린샷은 공개 스킬이나 저장소에 올리지 않는다. Cookie, Set-Cookie, Authorization, 토큰, 전체 요청 헤더와 개인 데이터는 출력하지 않는다. 공개 스킬·예제·검증 파일에는 내부 서비스 주소와 기기별 경로도 포함하지 않는다.

완료 보고에서 `코드 적용`, `로컬/고정 표본 검증`, `실제 출처 수집`, `저장·분석·게시` 중 확인한 범위를 밝힌다. 대기 중이면 다음 시도 가능 시각과 아직 확인하지 못한 결과를 구체적으로 쓴다. 새 예약 작업이나 메시지 전송은 별도 요청이 있을 때만 설정한다.
