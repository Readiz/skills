# Codex에서 에이전트를 나누어 쓰는 패턴

정리 기준: 2026-10-27. 이 문서는 한 대화의 메인 모델과 하위 에이전트가 협력할 때 작업을 나누는 참고 자료입니다. 역할 설정과 위임 실행 기준은 [Codex 모델과 에이전트 운영](codex-agent-workflow.md)을 따릅니다. 여기서는 작업 크기와 위험에 따라 조사와 구현, 검토를 어떻게 나눌지, 결과를 어떻게 비교할지 설명합니다.

공식 에이전트 기능과 설정 형식은 [Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents), 지침 파일의 적용 범위는 [AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md)를 확인하세요. 공개된 사용자 후기와 오픈소스 프로젝트는 운영 아이디어의 사례이며 제품 동작을 보장하는 근거와는 구분합니다.

## 작업 크기와 위험에 따른 분담

| 작업 유형 | 예시 | 권장 흐름 |
| --- | --- | --- |
| 작은 문구 수정 | 버튼 설명의 오탈자, 이미 확정된 한 줄 안내 수정 | 메인이 직접 고치고 문맥을 확인합니다. 조사나 별도 리뷰를 위한 에이전트 실행은 대개 필요하지 않습니다. |
| 범위가 있는 기능 개발 | 설정 화면에 선택 항목과 저장 동작 추가 | Sol이 요구사항, 수정 범위, 수용 조건을 정한 뒤 Luna 구현자에게 실제 작업을 맡깁니다. 메인은 diff와 동작 검증을 확인합니다. 선행 조사가 필요하면 Terra 조사 결과를 받은 뒤 구현 범위를 확정합니다. |
| 웹 UI 오류 | 특정 브라우저에서 메뉴가 겹치거나 버튼이 동작하지 않음 | 브라우저와 재현 환경에 연결된 Terra 조사자가 실제 화면과 오류를 확인합니다. 조사 결과에 근거해 재현 조건을 좁히고, Luna 구현자가 수정한 뒤 메인이 같은 조건에서 확인합니다. 문서 검색만 했다면 화면 관찰로 보고하지 않습니다. |
| 고위험 변경 | 인증 경계, 동시성, 데이터 이관처럼 여러 실행 경로에 영향을 주는 변경 | Sol이 범위와 검증 계획을 설계하고 필요한 조사를 거쳐 구현을 위임합니다. 위험이 정당화되면 Luna 구현 뒤 별도 Sol reviewer가 diff와 실행 경로를 독립 검토하고, 메인이 결과를 통합해 최종 검증합니다. |

Sol이 메인인 구성에서는 설계와 수용 조건을 먼저 확정하고 필요한 역할을 실제로 호출합니다. 먼저 Sol이 설계와 수용 조건을 정하고, 필요한 경우 Terra가 조사합니다. Luna가 구현한 뒤 위험이 큰 변경은 Sol reviewer가 독립 검토하고, 메인이 결과를 통합해 최종 검증합니다. 조사와 구현이 서로 기다릴 필요가 없을 때만 병렬로 나눕니다. 작은 수정은 직접 처리할 수 있으며, 단순히 위임이 번거롭다는 이유로 비사소한 구현을 모두 직접 끝낸 뒤 하위 에이전트를 시험 호출하지 않습니다.

Astra가 메인일 때는 위 순서를 강제하지 않습니다. Astra가 직접 수행, 위임, 병렬화와 검증 범위를 판단하며 메인 모델과 Effort 선택을 유지합니다. 다른 모델이 메인이어도 사용자 선택을 유지하고 작업에 맞춰 분담합니다. 실제로 사용 가능한 모델, 도구, 권한과 동시 작업 한도를 확인한 뒤 요청합니다. 세부 사용자 공통 기준은 [codex-agent-workflow.md](codex-agent-workflow.md)에 있습니다.

## 역할 작업 패킷

작업을 위임할 때는 요청을 독립적으로 실행하고 결과를 검토할 수 있을 만큼 구체적으로 씁니다. 다음 항목을 필요한 정도로 포함합니다.

```text
목표: 설정 화면에서 알림을 끄고 켜는 선택을 저장한다.
허용 파일: src/settings/notifications.ts, src/settings/NotificationsPanel.tsx
수정 금지 범위: 데이터베이스 스키마와 다른 설정 화면
수용 조건: 선택값이 새로고침 뒤에도 유지되고 기존 기본값 동작이 보존된다.
필요한 검사: 관련 단위 검사, 변경된 화면에서 저장한 뒤 다시 들어왔을 때의 값 확인
반환할 내용: 수정 파일, 구현 요약, 실행한 검사와 결과, 미확인 동작 또는 막힌 점
```

조사 역할에는 조사할 질문과 허용된 브라우저 및 검색 도구를 적고, 실제 관찰과 추론을 구분해 달라고 요청합니다. 검토 역할에는 파일 변경을 금지하고 회귀, 보안, 동시성 등 검토 범위와 심각도별 근거를 요청합니다. 역할별 TOML이나 모델 선택 예시는 [codex-agent-workflow.md](codex-agent-workflow.md)를 참고하세요.

작업 패킷을 작성했다고 위임이 완료된 것은 아닙니다. 현재 대화에서 하위 에이전트가 실행됐는지와 반환 결과를 확인합니다. 설정 파일만 저장한 것, 별도 CLI에서 설정을 시험한 것, 현재 대화에서 실제로 위임한 것은 서로 다른 근거입니다. 별도 CLI 시험은 CLI 설정을 확인하는 데 유용할 수 있지만 현재 대화의 위임을 증명하지는 않습니다.

## 사용자 경험과 공개 구성 사례

사례는 설계 아이디어를 읽는 자료로 사용하고 측정된 일반 성능이나 공식 보장으로 확대하지 않습니다.

- Reddit의 한 사용자는 Astra Ultra를 메인으로 두고 기본 Sol과 쉬운 작업의 Luna를 하위 역할로 활용한 경험을 설명합니다. 작성자가 통제 벤치마크를 하지 않았다고 밝혔으므로 구성에 대한 개인 후기입니다. [Astra Ultra with Sol/Luna subagents has been working really well for me](https://www.reddit.com/r/codex/comments/1wqwkza/astra_ultra_with_solluna_subagents_has_been/)
- [codex_workflow](https://github.com/viettran-edgeAI/codex_workflow)는 Light 작업은 직접 처리하고 Heavy 작업은 구현과 검증, 조사를 나누는 공개 구성을 보여줍니다. 속도나 사용량 절감 설명은 제작자의 주장과 초기 사례로 읽고 보편적 절감률로 인용하지 않습니다.
- [codex-astra-luna-orchestrator](https://github.com/donvito/codex-astra-luna-orchestrator)는 Astra/Sol/Luna 메인 프로필과 조사, 구현, 시험 역할을 두고 상위 검토 뒤 메인이 통합하는 구조를 제시합니다. 프로젝트 설치를 권하는 자료가 아니라 역할 설계와 측정 항목을 참고하는 사례입니다. 부속 [토큰 사용량 측정 가이드](https://github.com/donvito/codex-astra-luna-orchestrator/blob/main/guides/token-usage.md)는 반복 실행과 캐시, 실제 호출된 역할, 실행 시간, 계정 전체 사용량을 구분해 기록합니다.
- [GPT-5.6 Sol cannot specify subagent models 이슈](https://github.com/openai/codex/issues/31814)는 2026-07-09에 등록된 특정 사용자의 V2 spawn 스키마 보고이며 현재 닫힌 이슈입니다. 모든 버전에 현재 남은 제한이나 수정 완료를 입증하지 않습니다. 역할별 모델과 Effort를 가정하지 말고 실제 실행에서 확인해야 한다는 사례로만 참고합니다.

제품의 공식 동작은 위 사용자 후기나 저장소보다 공식 [Subagents 문서](https://learn.chatgpt.com/docs/agent-configuration/subagents)와 [AGENTS.md 문서](https://learn.chatgpt.com/docs/agent-configuration/agents-md)를 기준으로 확인합니다.

## 대표 작업으로 비교하기

직접 처리와 위임 구성을 비교하려면 같은 저장소 상태와 대표 작업을 여러 번 실행하고, 수행 조건을 함께 기록합니다. 측정 전에 작업 요구사항, 시작 시점의 변경 상태, 모델과 Effort, 도구, 검사 범위를 고정합니다. 실행 순서를 섞고 반복 횟수를 기록해 한 번의 우연한 결과를 일반화하지 않습니다.

비교 표에는 적어도 다음을 남깁니다.

| 항목 | 기록 방법 |
| --- | --- |
| 결과 품질 | 수용 조건 통과 여부, 발견된 결함의 수와 심각도, 빠뜨린 동작 |
| 총 경과 시간 | 요청 시작부터 검증된 결과까지. 조사와 대기, 통합, 재작업 시간을 모두 포함하고 각 구간도 따로 적습니다. |
| 검사 | 실행한 검사 이름과 결과, 실제 UI 확인 여부, 미실행 검사 |
| 재작업 | 메인이 수정한 하위 결과, 되돌린 변경, 이유와 추가 시간 |
| 에이전트 호출 | 실제 실행된 역할과 모델/Effort, 호출 수, 각 호출의 결과. 초기 상속 컨텍스트와 역할 실행 컨텍스트를 구분합니다. |
| 토큰 | 캐시 읽기와 쓰기, 미캐시 입력과 출력의 포함 여부 및 출처를 구분합니다. 보고서나 계기판의 집계 범위도 적습니다. |
| 계정 사용량 | 계정 전체 5시간 창과 주간 사용량을 같은 계정에서 시작과 종료 시점에 기록합니다. 해당 작업 외의 동시 작업과 다른 세션 사용 여부도 적습니다. |

반복/캐시가 포함된 토큰 수와 계정 전체 사용량 변화는 같은 수치가 아닙니다. 다른 세션이 실행 중이면 계정 창의 차이를 특정 작업의 비용으로 단정할 수 없습니다. 결과를 비교할 때 사용량과 시간만으로 품질을 대신하지 않습니다. 정형 보고서는 비교 실험이나 사용자 요청에 필요한 경우에 작성하고, 일반 작업마다 모든 지표 보고를 강요하지 않습니다.
